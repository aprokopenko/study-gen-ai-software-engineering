# 7. Low-Level Tasks (Spending-Caps Backend)

Each task is one implementable slice — sized for a single pull request — listed in dependency order. Each task names the **Mid-Level Objectives** (M-ids) and **Functional Flow steps** (F-ids) it serves, lists the files/artifacts it creates or updates, gives a one-line prompt an engineer or AI agent can act on, and ends with **concrete acceptance criteria**. Tasks add their own env vars and Makefile targets as they land — T01 only ships what its own acceptance needs.

Stack locked in T01: **Python 3.12 + FastAPI + SQLAlchemy 2.0 + Alembic + PostgreSQL**.

## T11 — Sessions, refresh, device-bound step-up

**Serves** — M1 (session lifecycle), M2 (step-up). F1 step 5, F2 step 1.

**Prompt**

Provide FastAPI `Depends` for `current_user` and `require_stepup`. **Files**

app/core/security/tokens.py              # issue / verify session, refresh, stepup
app/core/security/challenge.py           # nonce store (Redis) with 60s TTL
app/core/security/dependencies.py        # current_user, require_stepup
app/db/models/device_key.py
alembic/versions/XXX_device_keys.py
tests/core/test_security_tokens.py

```

**.env additions** — `JWT_SIGNING_KEY`, `JWT_ALG=HS256`, `SESSION_TTL_SECONDS=3600`, `REFRESH_TTL_SECONDS=604800`, `STEPUP_TTL_SECONDS=300`, `STEPUP_CHALLENGE_TTL_SECONDS=60`.

**Token shapes**

- **Session** — JWT with `sub=user_id`, `device_id`, `iat`, `exp`. 1 h TTL.
- **Refresh** — opaque random 256-bit string; `refresh_tokens.token_hash` is the SHA-256 of it. 7-day TTL. **Single-use**: each refresh rotates and revokes the old one.
- **Step-up** — JWT with `sub=user_id`, `device_id`, `stepup=true`, `iat`, `exp`. 5-min TTL.

**Endpoints**

- `POST /auth/refresh { refresh_token }` → `200 { session_token, refresh_token }`. Old refresh marked revoked; returning a revoked refresh → `401`.
- `POST /auth/devices/register { device_id, public_key_pem }` → `201`. Stores the pubkey for `(user_id, device_id)`. Re-registration with a different key revokes the previous one and writes an `AuditEvent`.
- `POST /auth/stepup/challenge` → `200 { challenge: <base64-32-bytes> }`. Server generates a random nonce, stores it under `(user_id, device_id)` for 60 s in Redis.
- `POST /auth/stepup/verify { challenge, signature_b64 }` → `200 { stepup_token }`. Verifies signature against the registered device pubkey; consumes the challenge (one-shot).

**New table — `device_keys`**

`id`, `user_id fk`, `device_id text`, `public_key_pem text`, `created_at`, `last_used_at`, `revoked_at nullable`. **Unique** `(user_id, device_id)` partial-where `revoked_at IS NULL`.

**Acceptance**

- A protected endpoint depending on `current_user` accepts a valid session token and rejects expired / tampered ones with `401`.
- Calling `/auth/refresh` rotates the refresh: prior token returns `401` on next use.
- `/auth/devices/register` stores the pubkey; second registration with a different key revokes the old one (verified by row state).
- `/auth/stepup/challenge` then `/auth/stepup/verify` with a valid Ed25519 (or RSA) signature returns a step-up token whose JWT carries `stepup=true` and `exp = iat + 300`.
- Replay: re-submitting the same `(challenge, signature)` after a successful verify returns `400` (challenge already consumed).
- A dependency `require_stepup()` returns `403` when the request lacks a valid step-up token (used by T13 and T18).

## T15 — Ingestion worker

**Serves** — M5, M6, M7, M11. F3 steps 4–9. Uses T03 / T04 / T07 / T09 / T12.

**Prompt**
> Long-running worker that consumes from the ingestion stream. For each payload: dispatch to the source's adapter (T12); idempotency-gate on `(adapter_id, external_event_id)`; classify as new / merge / refund; persist with FX-converted amounts and categorisation from `mcc_map_v1`; on success, enqueue a cap-evaluation message for T16. Each item processed in a single DB transaction.

app/ingestion/merge.py                     # pending → posted merge logic
app/ingestion/fx.py                        # Decimal-safe conversion

```

**.env additions** — `INGESTION_QUEUE_STREAM=ingestion`, `INGESTION_CONSUMER_GROUP=ingestion-workers`.

**Make targets added** — `run-ingestion` (long-running worker entrypoint).

**Pipeline steps** *(one DB transaction per payload)*

1. Adapter lookup by `adapter_id` → `adapter.transform(payload)` → `NormalizedTransactionEvent`.
2. Idempotency gate: drop silently if `(adapter_id, external_event_id)` already in `transactions` (increment metric).
3. Classify on `status`: new / merge / refund.
4. **Merge**: select by `(adapter_id, external_transaction_id) WHERE reverses_transaction_id IS NULL`; apply only if incoming `update_seq` > stored.
5. **New**: insert. **Refund**: insert with `reverses_transaction_id` linked to the original.
6. FX: `base_amount_minor = banker_round(Decimal(original_amount_minor) × Decimal(fx_rate))`.
7. Categorise: `category = mcc_map_v1.get_bucket(mcc)`; record `mcc_map_version`.
8. On commit success: enqueue cap-evaluation message to T16's stream; ack the queue message.

**Acceptance**

- Duplicate event `(adapter_id, external_event_id)` → second is dropped without insert; duplicate counter incremented.
- Pending then posted for the same `external_transaction_id` → one row, final `status='posted'`, `update_seq` of the posted event.
- Out-of-order: posted then pending (with smaller `update_seq`) → posted state preserved; second event ignored.
- Refund event → new row with `reverses_transaction_id` set; original row untouched.
- FX rounding test: a fixture with `original_amount_minor=12345`, `fx_rate=0.9012` → `base_amount_minor=11125` (banker's rounding); zero `float` usage asserted (test patches `float` import in module under test).
- Unmapped MCC → `category=Other`; `mcc_map_version` persisted.
- Handler raises → no ack; message redelivered (covered by T04, smoke-tested here).
- On successful persist, one evaluation message enqueued per affected `cap_id` (asserted via queue spy).

## T16 — Cap evaluator

**Serves** — M13, M14, M15. F3 steps 10–12, F4 step 4 (cap_reduced), F5 step 4 (recategorisation).

**Prompt**
> Worker consumes from the evaluation stream. For each event — new transaction, cap reduced, or recategorisation — recompute affected `period_spend_minor`, detect newly crossed thresholds (50 / 80 / 100), apply re-arm logic, write one `CapEvaluation` per crossing, and enqueue a notification dispatch message for T19. Pure evaluator function is unit-testable in isolation from the queue.

**Files**

```
app/domain/evaluation/__init__.py
app/domain/evaluation/evaluator.py         # pure function: state in, decisions out
app/domain/evaluation/worker.py            # queue consumer + DB I/O
app/cli/run_evaluator_worker.py
tests/domain/test_evaluator.py
tests/domain/test_evaluation_worker.py
```

**.env additions** — `EVALUATION_QUEUE_STREAM=evaluation`, `EVALUATION_CONSUMER_GROUP=evaluation-workers`.

**Make targets added** — `run-evaluator`.

**Evaluator algorithm** *(pure; no I/O)*

Given `(cap, current_period, delta_amount_minor, cause)`:

1. `new_spend = current_period.period_spend_minor + delta_amount_minor`.
2. For each threshold in `[50, 80, 100]`:
   - If `armed_for(threshold)` AND `new_spend ≥ threshold/100 × cap.amount_minor` → record crossing; disarm.
   - Else if `not armed_for(threshold)` AND `new_spend < threshold/100 × cap.amount_minor` → re-arm; no firing.
3. Special: when `cause == cap_reduced` and `new_spend ≥ cap.amount_minor`, fire 100% with `cause='cap_reduced'` even if previously disarmed (one-shot per save).
4. Return `[CapEvaluation, …]` + updated armed flags.

Worker wraps the pure function with: load current period → call evaluator → write `CapEvaluation` rows + update `current_periods.threshold_*_armed` and `period_spend_minor` → enqueue notification messages (one per new crossing) → ack.

**Acceptance**

- 49% → 51% (USD 100 cap, transaction $2) → exactly one `CapEvaluation` with `threshold_pct=50`, `cause='spend'`.
- 49% → 81% (one big transaction) → two `CapEvaluations` for 50 and 80, in ascending order.
- 81% → 49% via refund → both 50 and 80 re-arm; **no** firing.
- 49% → 81% after refund → 50 and 80 fire again.
- Recategorisation moving $200 from Dining cap to Groceries cap → evaluator runs for both caps; Dining may re-arm, Groceries may cross thresholds.
- Cap reduced from $200 to $100 while current spend is $120 → `CapEvaluation(threshold_pct=100, cause='cap_reduced')` emitted on cap-save (not on next transaction).
- Pure evaluator benchmark: 1000 evaluations < 100 ms (asserts the function is allocation-light enough to hit the p95 < 100 ms SLO once DB I/O is included).
- Each crossing enqueues one notification message addressed to T19.

## T20 — Monthly rollover + daily reconciliation jobs

**Serves** — M18, M19. F7, F8.

**Prompt**
> Two scheduled jobs. **Rollover**: hourly cron; for each user whose local time has just crossed into the 1st of the month, snapshot every active cap's current period into `period_snapshots`, then open a fresh `current_periods` row with `period_spend_minor=0` and all thresholds armed. **Reconciliation**: daily; for every period closed in the past 24 h, verify `snapshot.period_spend_minor == sum(in-scope transactions) + sum(adjustments)`; on match write `reconciliation_ok` audit event; on mismatch write `reconciliation_incident` audit event and raise an ops alert. Late-arriving transactions with `posted_at` inside a closed period are persisted by T15 along with an `Adjustment` row pointing at the relevant snapshot — verify that integration here.

**Files**

```
app/jobs/__init__.py
app/jobs/rollover.py
app/jobs/reconciliation.py
app/jobs/scheduler.py                      # simple cron-driven dispatcher (APScheduler or cron + entrypoint)
app/cli/run_jobs.py
tests/jobs/test_rollover.py
tests/jobs/test_reconciliation.py
tests/jobs/test_late_arrival_adjustment.py
```

**.env additions** — `JOBS_TIMEZONE=UTC`, `RECONCILIATION_LOCAL_TIME=04:00`, `ROLLOVER_BATCH_SIZE=500`.

**Make targets added** — `run-jobs`.

**Rollover algorithm** *(hourly)*

1. For the current UTC hour, identify users whose IANA timezone makes "now" the first hour of the 1st of the month.
2. Batch them (`ROLLOVER_BATCH_SIZE` per transaction).
3. For each user × each active cap: insert `period_snapshots` from `current_periods`; reset `current_periods` (new start/end in local TZ, `period_spend_minor=0`, all thresholds armed); write `AuditEvent(actor_type='system', action='period_rollover')`.

**Reconciliation algorithm** *(daily)*

1. For every `period_snapshots` row with `snapshotted_at` in the last 24 h:
2. `expected = Σ(transactions.base_amount_minor WHERE in scope AND posted_at ∈ [period_start, period_end]) + Σ(adjustments.base_amount_minor WHERE period_snapshot_id = snapshot.id)`.
3. If `expected == snapshot.period_spend_minor` → write `AuditEvent(action='reconciliation_ok')`.
4. Else → write `AuditEvent(action='reconciliation_incident', after_state={expected, actual, diff})` and emit a structured ops-alert log line.

**Acceptance**

- A user in `Europe/Kyiv` (UTC+2 in standard time) has their rollover triggered at `22:00 UTC` on the last day of the month (= `00:00` local 1st).
- A user in `America/Los_Angeles` (UTC−8) has their rollover triggered at `08:00 UTC` on the 1st.
- New `current_periods` row has `period_spend_minor=0` and all three `threshold_*_armed=true`.
- Rollover writes one `AuditEvent` per cap snapshotted.
- A test inserts a transaction with `posted_at` inside an already-closed period; T15 (via dependency injection in the test) creates a transaction row AND an `Adjustment` row linked to the snapshot; the snapshot's `period_spend_minor` is unchanged.
- Reconciliation on a clean period emits `reconciliation_ok`; reconciliation on a period where a snapshot is manually tampered (via superuser, since the app role can't) emits `reconciliation_incident`.
- Bench: rollover processes 10 000 users × 5 caps each within 30 min in a single shard (M18 SLO).
- Bench: reconciliation on the same volume completes within 2 h (M19 SLO).
